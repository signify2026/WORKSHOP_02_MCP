Workshop Intro

Why Build a Custom MCP Server?

What is a Custom MCP?

A Model Context Protocol server you build and own. It wraps your internal APIs in typed, callable tools — so AI agents like Copilot can query Jira, write to Confluence, or trigger any workflow directly, without copy-pasting context.

Think of it as a structured bridge between Copilot and your internal systems — you define the tools, the AI decides when to call them.

When do you need one?

→Your tools sit behind a firewall — Signify's Jira Data Center, internal Confluence
→No public MCP server covers your internal systems
→Engineers repeat the same steps every sprint — copy ACs, paste results, write docs
→You need tools scoped to your team's exact workflow and data model
The official Atlassian Rovo MCP is Cloud-only. Signify's self-hosted Jira and Confluence need a custom bridge.

What you gain

✓Live data — Copilot reads directly from Jira, no stale copy-paste, no drift
✓One prompt replaces 10+ manual steps across Jira, VS Code, and Confluence
✓Team-wide — every engineer shares the same connection, no per-person setup
✓You control access — define exactly what the AI can touch and what it cannot

What we build today — signify-atlassian

search_issues— run JQL queries
create_page— publish content to Confluence

Build signify-atlassian MCP in 4 Steps

1

Install — one package

mkdir mcp-servers/signify-atlassian
cd    mcp-servers/signify-atlassian
npm init -y
npm install @modelcontextprotocol/sdk
3

Wire it — one block in mcp.json

// .vscode/mcp.json — add alongside playwright
{
  "servers": {
    "playwright": { /* existing */ },
    "signify-atlassian": {
      "command": "node",
      "args": ["./mcp-servers/signify-atlassian/server.js"],
      "env": { "ATLASSIAN_PAT": "${input:atlassian-pat}" }
    }
  }
}
4

Verify — MCP Inspector before VS Code

ATLASSIAN_BASE_URL=https://jira.signify.com \
ATLASSIAN_PAT=*** \
npx @modelcontextprotocol/inspector node server.js

Click Tools. You should see get_issue, search_issues, and create_page. We add get_project_meta and create_issue live — Inspector will then show 5 tools.

2

Write the server — JavaScript example

import { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js';
import { StdioServerTransport } from '@modelcontextprotocol/sdk/server/stdio.js';
import { z } from 'zod';

const baseUrl = process.env.ATLASSIAN_BASE_URL;
const pat = process.env.ATLASSIAN_PAT;
if (!baseUrl || !pat) throw new Error('Atlassian env vars missing');

const server = new McpServer({ name: 'signify-atlassian', version: '1.0.0' });

server.tool(
  'get_issue',
  'Fetch one Jira issue by key from a self-hosted Atlassian instance.',
  { issueKey: z.string().describe('Jira key e.g. US-4821') },
  async ({ issueKey }) => {
    const issue = await fetch(
      `${baseUrl}/rest/api/2/issue/${issueKey}`,
      { headers: { Authorization: `Bearer ${pat}` } }
    ).then(r => r.json());

    return { content: [{ type: 'text', text: JSON.stringify({
      key: issue.key,
      summary: issue.fields.summary,
      status: issue.fields.status.name,
      description: issue.fields.description
    }, null, 2) }] };
  }
);

// search_issues and create_page follow the same pattern
await server.connect(new StdioServerTransport());

Tool list

When VS Code starts the server it calls tools/list. The LLM sees get_issue, search_issues, and create_page with descriptions and schemas.

Typed call — not a prompt

Your handler receives structured JSON — { issueKey: "US-4821" } — never the user's raw sentence. Zod rejects bad arguments before Jira is touched.

stdio transport

VS Code spawns your server with node. No port, no deploy step, no Cloud-only OAuth flow. Perfect for a workshop and for internal Data Center APIs.

MCP is language-neutral. We use Node.js here because the workshop is fast to follow, but the same tool contract can be implemented in Python, Java, Go, or C#. Discover tools by asking: what repeated work do engineers do, what inputs are needed, what should be returned, and is it read-only or write-capable?

Build with Copilot

Let Copilot Write the Boilerplate — You Write the Spec

Give Copilot a spec, not a vague request

Copilot is excellent at SDK boilerplate. It is not excellent at guessing your internal Jira URL, auth method, or Confluence payload shape. TypeScript is optional; the contract is what matters.

"Create a Node.js MCP server called signify-atlassian.
 Tools:
 1. get_issue(issueKey: string) → GET /rest/api/2/issue/{key}
 2. search_issues(jql: string, maxResults: 1-50)
 3. create_page(spaceKey, title, body) → POST /rest/api/content
 4. get_project_meta(projectKey: string) → GET /rest/api/2/project/{key}
 5. create_issue(projectKey, summary, description, issueType)

 Use ATLASSIAN_BASE_URL, CONFLUENCE_BASE_URL, ATLASSIAN_PAT.
 Use @modelcontextprotocol/sdk + Zod.
 Keep each tool description to one sentence."

What Copilot generates for you

✓ McpServer + StdioServerTransport setup
✓ Zod schemas with min/max constraints and useful describe() text
✓ Jira and Confluence fetch helpers with Bearer token auth
✓ Clear JSON return shapes for the LLM to reuse in later steps
✓ Startup env-var checks so failure happens before the demo starts

Copilot is great at

✓ SDK boilerplate in seconds
✓ Zod schemas from plain English
✓ Shared REST helper functions
✓ Adding tools via follow-up prompts
✓ Inspector-ready examples

Watch out for

⚠ Cloud endpoints when you need Data Center
⚠ Verbose tool descriptions
⚠ Hallucinated custom fields
⚠ Missing confirmation before writes
⚠ Secrets inside code or descriptions

How to discover useful tools

Read-only: get_issue, search_issues, get_page, search_pages, get_sprint_issues
Write: create_issue, add_issue_comment, transition_issue, create_page
Workflow: create_test_plan_from_issue, create_release_notes_from_jql, create_bug_from_failed_test
Rule: start with read-only tools. Add write tools only with confirmation, auditability, and tight input schemas.

The pattern: write a 5-line tool contract → ask Copilot for boilerplate → trim descriptions → run Inspector → wire in mcp.json.

Guardrails

Production Guardrails & Best Practices

One server, one job.

Give each MCP server a single, clear purpose — scoped servers are easier to audit and a breach stays contained.

  • Enable or disable servers independently
  • Rotate PATs per-server — no shared master token

Minimum access. No blind trust.

Read-only by default. Block internal IP ranges — AI clients can be prompt-injected into calling internal services.

  • Read secrets only from env vars — never hardcode
  • Never accept user-supplied URLs — use an allowlist

Handle failures deliberately.

Return isError: true for execution errors — the LLM backs off instead of retrying blindly.

  • Always include a human-readable message
  • Wrap every handler in try/catch — no crashes

Design your tools as prompts.

Tool descriptions are read by the LLM to decide when to call — write them like concise, accurate instructions.

  • Use namespaced names: jira_get_issue not get
  • stdio servers: never write to stdout — use stderr

Validate inputs. Cap outputs.

Check every argument with a schema before calling any API. Use Zod — reject unexpected fields explicitly.

  • Sanitise user text before embedding it in JQL
  • Sanitize outputs before returning to the model

Rate-limit every tool.

A stuck AI retry loop can fire 1,000+ calls/min. Cap reads at 120/min and writes at 10–30/min.

  • Apply per-session limits — one agent, one bucket
  • Include Retry-After in responses so the LLM waits

Log every call. No exceptions.

Record tool name, inputs, response status, and timestamp. No audit trail means no incident response.

  • Mask PATs and tokens before writing to any log store
  • Alert on error spikes — 4xx/5xx surges signal attacks

Inspector before you wire it in.

Run npx @modelcontextprotocol/inspector — it shows exactly what Copilot sees: tool names, descriptions, schemas.

  • Verify tools/list schemas & pin SDK — never @latest
  • Test all error paths — verify isError: true shape

DOM layer — what a recorder sees

Generated by the bundler at compile time. Contains build artefacts that change on every rebuild — invisible to users, meaningless to tests.

// Compile-time artefacts — never stable
.ClassFilterTabs_tab__a4f92        // CSS module hash
#tab-class-a-btn                     // internal generated ID
xpath=//button[@aria-selected][1]   // positional index

A11y tree — what browser_snapshot reads

Built by the browser at runtime from ARIA attributes and HTML semantics. Reflects what users see and screen readers announce — set by engineers, not build tools.

// Semantic contract — changes only when UX changes
role="tab"  name="All"          // ARIA role + visible label
role="tab"  name="Current"      // set by the component
aria-selected="true"           // ARIA state contract
Selector hierarchy — follow this order, every time
1
getByRole('tab', { name: 'All' })Always first
ARIA role + visible label. Survives CSS rebuilds, component renames, and UUI version upgrades.
2
getByLabel('Student name')Form controls
For inputs, selects, checkboxes. Tied to the accessible label — not the input's generated ID.
3
getByText('Show All Students')Visible text
For buttons and links without an explicit ARIA role. Breaks only when the copy itself changes — which is intentional.
✕
.ClassFilterTabs_tab__a4f92  ·  xpath=//div[1]Never generate
CSS hashes and positional XPath. Break on every rebuild — and MCP never produces these when it reads from the accessibility tree.

Three Modes — Three Layers of Quality

Snapshot Mode

Default No flags needed

Reads the accessibility tree — roles, names, and ARIA states as structured text. Fast and token-efficient.

"playwright": {
  "command": "npx",
  "args": ["-y", "@playwright/mcp@latest"]
}
Tools available:
browser_navigate browser_snapshot browser_click

Use for: /generate-tests and /repair-locators. Everything in today's demo runs here.

Vision Mode

--caps=vision

Adds pixel screenshots alongside the accessibility tree. For visual components the a11y tree cannot fully describe.

"args": [
  "-y", "@playwright/mcp@latest",
  "--caps=vision"   // enables screenshots
]
Adds:
browser_screenshot
Use for: /validate-ui (Figma comparison), canvas charts, SVG dashboards, drag-and-drop UIs.

--caps=devtools

Exposes Chrome DevTools Protocol data — console logs, network requests, performance metrics, security headers.

  "--caps=devtools"  // CDPtools
]
Adds:
browser_console_messages browser_network_requests

Catches invisible defects: silent 401s, third-party console errors, performance regressions — things Snapshot and Vision miss entirely.

Why this matters vs just running tests

Tests verify behaviour — screenshots verify appearance

AC-4 says "layout matches the Figma design." A passing test doesn't prove that. The screenshot comparison does. Both are needed.

Fix-and-revalidate loop

If the spacing is wrong, MCP proposes a CSS fix, applies it (with your confirmation), then takes another screenshot. One conversation — no manual back-and-forth.

browser_snapshot vs browser_screenshot

browser_snapshot → accessibility tree → use for test generation
browser_screenshot → pixel image → use for visual validation. They are not interchangeable.

Re-validate after every design change

Run /validate-ui after any CSS change, component update, or UUI upgrade. Catches subtle spacing differences that passing E2E tests won't surface.

Tip: Keep the Figma reference PNG (src/assets/figma-analysis/class-filter-tabs.png) in version control. When the design intentionally changes, update the PNG in the same commit — the validation step then tracks the new baseline.

// The 4-part structure for ClassFilterTabs
"Open a browser at localhost:3000.
Navigate to the Class Filter Tabs section.

The component has tabs: All, Current,
Upcoming, Past (EPMCDMETST-45161 AC-1).

Why this works: the trigger "Open a browser" invokes browser_navigate + browser_snapshot. Without it, Copilot stays in chat and invents selectors from memory.

What MCP generates — one test per AC
// AC-1: all 4 tabs are rendered
test('renders all 4 filter tabs', async ({ page }) => {
  for (const label of ['All','Current','Upcoming','Past']) {
    await expect(
      page.getByRole('tab', { name: label })
    ).toBeVisible();
  }
});

// AC-2: 'All' is selected by default
test('All tab selected by default', async ({ page }) => {
  await expect(
    page.getByRole('tab', { name: 'All' })
  ).toHaveAttribute('aria-selected', 'true');
});

// AC-3: clicking updates state
test('clicking Current updates tab', async ({ page }) => {
  await page.getByRole('tab', { name: 'Current' }).click();
  await expect(
    page.getByRole('tab', { name: 'Current' })
  ).toHaveAttribute('aria-selected', 'true');
});

Scope Your Prompts — One Component at a Time

What fills the context window

One giant prompt for the whole app

// What burns the context window
"Open a browser at localhost:3000.
Test the entire Learning Dashboard.
Include the header, class filter tabs,
leaderboard table, pagination, modals,
user profile, and all sidebar navigation.
Cover all edge cases and error states.
Generate a complete test suite."

// What happens:
// - MCP tool calls: 12+ browser_snapshot calls
// - Context fills after 3rd component
// - Copilot "forgets" the first feature
// - Session degrades → useless output

Why MCP makes it worse

Each browser_snapshot injects the full accessibility tree into the context. Snapshotting 5 components = 5× the context consumed — on top of the conversation history.

Each snapshot adds hundreds of tokens. A fresh Copilot session with a scoped prompt stays coherent from start to finish.

The fix: one feature → one prompt → one test file

Scoped prompt for ClassFilterTabs only

// What keeps the context clean
"Open a browser at localhost:3000.
Navigate to the Class Filter Tabs section.

Generate a @playwright/test for:
  AC-1: 4 tabs are rendered
  AC-2: 'All' tab is selected by default
  AC-3: clicking a tab updates state

Use only getByRole and getByText.
Output to tests/e2e/class-filter-tabs.spec.ts"

// What happens:
// - MCP tool calls: 1 browser_navigate +
//   1–2 browser_snapshot calls only
// - Full session stays coherent
// - Output is clean and reviewable
The scoping rule
1

One component per prompt — ClassFilterTabs, not the whole Dashboard

2

One user flow per prompt — tab selection, not tab selection + pagination + modals

3

One output file per prompt — name it explicitly: class-filter-tabs.spec.ts

The demo uses exactly this pattern. /validate-ui targets ClassFilterTabs only. The LeaderboardTable gets its own separate prompt and test file.

Bonus — DevTools Mode

Catching Invisible Defects — What Snapshot Misses

The invisible defect scenario

Component renders ✓ Test passes ✓ But…

  • Data API returns 401 Unauthorized — widget shows cached stale data
  • Third-party dependency throws console.error silently on load
  • Page makes 14 duplicate network requests — invisible in CI, kills mobile performance
Snapshot and Vision cannot see any of this. They only see what the browser rendered.
One config change

Add --caps=devtools to mcp.json

"playwright": {
  "command": "npx",
  "args": [
    "-y", "@playwright/mcp@latest",
    "--caps=devtools"  // <-- add this
  ]
}

Reload VS Code after saving. Now Copilot has browser_console_messages and browser_network_requests alongside its usual snapshot tools.

DevTools-mode prompt

Example prompt

"Open a browser at localhost:3000.
Load the Support Team Widget.
Check the browser console for
any errors or warnings.
List all network requests and flag
any that returned a non-2xx status."

Tool call sequence

browser_navigate → opens localhost:3000
browser_console_messages → returns all errors/warnings
browser_network_requests → returns all requests with status codes

What DevTools mode catches

  • Silent 401 / 403 / 500 on data APIs
  • Third-party script console errors
  • Duplicate or redundant network requests
  • Security header violations
  • Slow responses hurting performance

Token cost: DevTools + Vision combined (--caps=vision,devtools) is expensive. Use default Snapshot for CI. Use DevTools for pre-release exploratory testing.
