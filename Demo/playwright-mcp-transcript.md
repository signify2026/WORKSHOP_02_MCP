[pause]

And below that — `xpath=//button[@aria-selected][1]` — a positional XPath. That breaks the moment you add a fifth tab, or reorder the existing four.

[beat]

[pause]

`page.getByRole('tab', { name: 'All' })`

[pause]

This came from the accessibility tree. It's tied to the ARIA role and the visible label — not to CSS internals. Rename the CSS class, upgrade UUI, restructure the div — none of that touches this selector.

[beat]

The only thing that breaks this test is renaming the tab label from "All" to something else.

[pause]

And if you've done that — the test should fail. The acceptance criteria changed. That's the test doing exactly what it's supposed to do.

[pause]

That is the difference between a test that breaks every sprint, and a test that breaks when the behaviour actually changes.

## Slide 3 — MCP Mental Model + Setup
*[2.5 minutes. Advance to Slide 3.]*

Let me build the mental model for why this works.

[pause]

Playwright MCP reads the accessibility tree. Not the DOM.

[beat]

Left side — DOM selectors. `.ClassFilterTabs_tab__a4f92` is a CSS Modules artifact. It changes every build. `#tab-class-a-btn` — some engineer added that ID, another removed it next sprint. `xpath=//div[@data-v-12ab]` — a Vue scoping hash, mutates with every rebuild.

[pause]

Right side — accessibility tree. `getByRole('tab', { name: 'All' })`. The a11y tree is what a screen reader reads. It reflects what the user sees and what the component is supposed to do. Rename the CSS class? The a11y tree still says "All" with role="tab". Upgrade UUI? Same. Restructure the div? Same.

[beat]

The accessibility tree is stable because it reflects intent. The DOM is volatile because it reflects implementation.

[pause]

And the setup to get this working is five lines.

[pause]

`.vscode/mcp.json`. `servers`. `playwright`. `command: npx`. `args: -y @playwright/mcp@latest`. `type: stdio`.

[pause]

That is it. No API token. No global installation. Commit this file and every engineer who clones the repository gets Playwright MCP automatically. Zero individual setup.

## Slide 4 — Prompt Anatomy
*[2 minutes. Advance to Slide 4.]*

Now — what actually triggers MCP to use the browser.

[pause]

Every effective prompt has four parts. They're on the four blue cards.

[beat]

One — the trigger. "Open a browser and navigate to..." Without this exact phrase, Copilot stays in chat mode. MCP tools are never called.

Two — context. Name the specific feature. Not "the dashboard." The specific component.

Three — framework. Pin the output. "...using @playwright/test..."

Four — constraints. Set the selector rule. "...use only getByRole and getByText."

[pause]

Look at the two examples at the bottom.

[beat]

The good prompt. "Open a browser at localhost:3000. Navigate to the Class Filter Tabs. Use only getByRole." — MCP calls `browser_navigate`, then `browser_snapshot`. Reads the real app. Writes real selectors.

[pause]

The bad prompt. "Generate a Playwright test for the filter tabs." No browser trigger. MCP tools are never called. Copilot invents `[data-testid="tab-all"]` and `#filter-tab-1`. Those don't exist. Tests fail on the first run. You spend an hour debugging a prompt problem, not a code problem.

[beat]

Three words. "Open a browser." That is the unlock.

## Slide 7 — Validate Against Figma
*[2 minutes. Advance to Slide 7.]*

Step three of the pipeline — `/validate-ui`.

[pause]

I said earlier that `browser_screenshot` and `browser_snapshot` are not the same tool.

[beat]

`browser_snapshot` — accessibility tree — use it to generate tests. That's what we just ran.

`browser_screenshot` — pixel image — use it here, to verify the rendered component matches the Figma design.

[pause]

The flow: navigate, screenshot, compare to `src/assets/figma-analysis/class-filter-tabs.png`, discrepancy report with severity, propose fixes, apply with confirmation, screenshot again, repeat.

[beat]

Why does this matter? AC-4 says "layout matches the Figma design." A passing test doesn't prove that. A test says "the tab switches when clicked." It says nothing about whether the font weight is wrong or the spacing is four pixels off. The screenshot comparison answers that question.

[pause]

And the fix loop means you never leave VS Code. Copilot proposes, you confirm, it applies, it screenshots again. One conversation.

## Slide 8 — Self-Healing
*[2 minutes. Advance to Slide 8.]*

Monday morning. UUI upgraded from version 6 to version 7 over the weekend. CI is red.

[pause]

The test with `.ClassFilterTabs_tab__a4f92` is failing. "Locator resolved to zero elements." The hash changed in the new version.

[beat]

Old approach: open DevTools, inspect the component, find the new hash, update the test, find the next broken test, repeat. Hours gone.

[pause]

New approach: paste the failing test into Copilot Agent Mode. Add: "navigate to localhost:3000, read the current accessibility tree, propose updated selectors using getByRole. Do not change the test logic — only fix the selectors."

[beat]

That last sentence is essential. Without it, Copilot might rewrite your assertions. You want the selector fixed. The intent preserved.

[pause]

What happens: `browser_navigate` → `browser_snapshot` → selectors returned from the live tree. Not from memory. From what exists right now, after the upgrade.

[beat]

Look at the table. Selector breaks in CI used to take four hours. Now it takes one prompt. Post-upgrade repair used to take a full sprint. Now thirty minutes. This is Pain #2 from the survey answered.
