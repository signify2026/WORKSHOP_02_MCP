Demo Story

US-4821 — Class Filter Tabs

User Story
US-4821 Priority 2 — High

Implement Class Filter Tabs

As a learner, I want to filter classes by category using horizontal tab buttons — All, Current, Upcoming, Past — so I can quickly navigate between class views.

Acceptance Criteria — what the tests must verify
AC-1
4 tabs rendered: All, Current, Upcoming, Past — each with a count badge
AC-2
Active tab is visually distinguished — highlighted underline or background
AC-3
Clicking a tab updates the active state and filters the content below
AC-4
Component uses UUI TabButton — layout matches Figma design

The Problem — Concrete

This Is the Test That Breaks Every Sprint

What a code recorder produces for ClassFilterTabs

DOM-coupled — breaks on rebuild

// Tab identified by CSS Module hash
// → breaks every time component is rebuilt
page.locator(
  '.ClassFilterTabs_tab__a4f92'
).first().click();

// Tab state by DOM index
// → breaks if tabs reorder or one is added
page.locator(
  'xpath=//button[@aria-selected][1]'
);

What breaks it (happens every sprint)

  • UUI TabButton version bump → new CSS hash
  • Component rename ClassFilter → TabFilter → new module name
  • Add a 5th tab → XPath index shifts
  • CSS Modules rebuild with new content hash
What Playwright MCP generates instead

Accessibility-tree coupled — survives all of the above

// Tab by ARIA role + visible label
// → survives hash changes, renames, reorders
page.getByRole('tab', { name: 'All' })
page.getByRole('tab', { name: 'Current' })
page.getByRole('tab', { name: 'Upcoming' })
page.getByRole('tab', { name: 'Past' })

// AC-2: active tab state
await expect(
  page.getByRole('tab', { name: 'All' })
).toHaveAttribute('aria-selected', 'true');

The only thing that breaks this test is changing the tab label from "All" to something else — which is intentional, the AC itself changed. That's exactly what you want.

Pain #1 in the survey: "Every UI change breaks existing automation suites due to changed HTML element IDs, locators, and selectors." — the CSS hash is precisely this. The demo fixes it at the source.

Setup

How MCP Sees Your App — & 5-Line Setup

DOM selectors — fragile

// Breaks on CSS module rebuild or HTML refactor
page.locator('.ClassFilterTabs_tab__a4f92')
page.locator('#tab-class-a-btn')
page.locator('xpath=//div[@data-v-12ab]')

Hash changes every build. ID removed next sprint. XPath breaks on any restructure.

Accessibility tree — stable

// browser_snapshot reads the a11y tree, not the DOM
page.getByRole('tab', { name: 'All' })
page.getByLabel('Student name')
page.getByText('Show All Students')

Tied to what users see. Survives class renames, framework upgrades, and component refactors.

Demo: Generate

Generating Tests from Acceptance Criteria

4
Currently running
/generate-tests — Playwright MCP reads the accessibility tree of ClassFilterTabs and generates specs from ACs
The prompt anchored to US-4821 ACs
// The 4-part structure for ClassFilterTabs
"Open a browser at localhost:3000.
Navigate to the Class Filter Tabs section.

The component has tabs: All, Current,
Upcoming, Past (US-4821 AC-1).
The 'All' tab is active by default (AC-2).
Clicking a tab filters the list below (AC-3).

Generate a @playwright/test for each AC.
Use only getByRole and getByText selectors."

Why this works: the trigger "Open a browser" invokes browser_navigate + browser_snapshot. Without it, Copilot stays in chat and invents selectors from memory.

What MCP generates — one test per AC
// AC-1: all 4 tabs are rendered
test('renders all 4 filter tabs', async ({ page }) => {
  for (const label of ['All','Current','Upcoming','Past']) {
    await expect(
      page.getByRole('tab', { name: label })
    ).toBeVisible();
  }
});

// AC-2: 'All' is selected by default
test('All tab selected by default', async ({ page }) => {
  await expect(
    page.getByRole('tab', { name: 'All' })
  ).toHaveAttribute('aria-selected', 'true');
});

// AC-3: clicking updates active state
test('clicking Current updates active tab', async ({ page }) => {
  await page.getByRole('tab', { name: 'Current' }).click();
  await expect(
    page.getByRole('tab', { name: 'Current' })
  ).toHaveAttribute('aria-selected', 'true');
});
Pain #3 — Context Window

"Chat Stops Working When Questions Are Big"

What fills the context window

One giant prompt for the whole app

// What burns the context window
"Open a browser at localhost:3000.
Test the entire Learning Dashboard.
Include the header, class filter tabs,
leaderboard table, pagination, modals,
user profile, and all sidebar navigation.
Cover all edge cases and error states.
Generate a complete test suite."

// What happens:
// - MCP tool calls: 12+ browser_snapshot calls
// - Context fills after 3rd component
// - Copilot "forgets" the first feature
// - Session degrades → useless output

Why MCP makes it worse

Each browser_snapshot injects the full accessibility tree into the context. Snapshotting 5 components = 5× the context consumed — on top of the conversation history.

Survey result: "Chat session stops working when questions are big — context window fills up before we get a useful output." This is the exact cause.

The fix: one feature → one prompt → one test file

Scoped prompt for ClassFilterTabs only

// What keeps the context clean
"Open a browser at localhost:3000.
Navigate to the Class Filter Tabs section.

Generate a @playwright/test for:
  AC-1: 4 tabs are rendered
  AC-2: 'All' tab is selected by default
  AC-3: clicking a tab updates active state

Use only getByRole and getByText.
Output to tests/e2e/class-filter-tabs.spec.ts"

// What happens:
// - MCP tool calls: 1 browser_navigate +
//   1–2 browser_snapshot calls only
// - Full session stays coherent
// - Output is clean and reviewable
The scoping rule
1

One component per prompt — ClassFilterTabs, not the whole Dashboard

2

One user flow per prompt — tab selection, not tab selection + pagination + modals

3

One output file per prompt — name it explicitly: class-filter-tabs.spec.ts

The demo uses exactly this pattern. /validate-ui targets ClassFilterTabs only. The LeaderboardTable gets its own separate prompt and test file.

Validating the Rendered UI Against Figma Design

Validation flow
browser_navigate to localhost:3000 component page
↓
browser_screenshot → captures rendered UI as pixel image
↓
Compare to src/assets/figma-analysis/class-filter-tabs.png
↓
Discrepancy report with severity — spacing, typography, color
↓

Why this matters vs just running tests

Tests verify behaviour — screenshots verify appearance

AC-4 says "layout matches the Figma design." A passing test doesn't prove that. The screenshot comparison does. Both are needed.

Fix-and-revalidate loop

If the spacing is wrong, MCP proposes a CSS fix, applies it (with your confirmation), then takes another screenshot. One conversation — no manual back-and-forth.

browser_snapshot vs browser_screenshot

browser_snapshot → accessibility tree → use for test generation
browser_screenshot → pixel image → use for visual validation. They are not interchangeable.

The repair — one prompt, not a sprint

Repair prompt template

"Test below fails after UUI upgrade.
Navigate to localhost:3000/class-filter-tabs,
read the current accessibility tree, propose
updated selectors using getByRole or getByText.
Do not change test logic — only fix selectors.

[paste failing test]"

MCP calls browser_navigate → browser_snapshot → returns selectors that exist right now in the live tree. Not from memory. Not guessed.
