The Pain

How Test Setup Looks Today

class-filter-tabs.spec.ts — setup block every tester hand-writes
// ~40 lines before a single expect() — in every spec file
let classId: string;

test.beforeEach(async ({ page }) => {
  // ① Auth — rotated monthly, breaks tests silently
  const token = await fetch('https://staging.signify/auth/token', {
    method: 'POST', body: JSON.stringify({ user: 'test_admin', pass: process.env.TEST_PASS })
  }).then(r => r.json()).then(d => d.token);

  // ② Create class — raw fetch, duplicated across 8 spec files
  classId = await fetch('https://staging.signify/api/classes', {
    method: 'POST', headers: { Authorization: `Bearer ${token}` },
    body: JSON.stringify({ name: 'Class A' })
  }).then(r => r.json()).then(d => d.id);

  // ③ Add students — 5 separate HTTP calls
  for (let i = 0; i < 5; i++)
    await fetch(`https://staging.signify/api/classes/${classId}/students`,
      { method: 'POST', headers: { Authorization: `Bearer ${token}` },
        body: JSON.stringify({ name: `Learner ${i}` }) });

  await page.goto(`http://localhost:3000/classes?id=${classId}`);
  await page.waitForSelector('[data-loaded="true"]');
});

test.afterEach(async () => { // ← skip this = next run is poisoned
  await fetch(`https://staging.signify/api/classes/${classId}`, { method: 'DELETE' });
});

What's wrong with this

↑~40 lines of setup before a single assertion — in every spec file
↑Auth logic duplicated across every spec — breaks when passwords rotate
↑Brittle raw API calls — any endpoint change breaks every test at once
↑If afterEach fails, the next CI run is polluted with stale data
↑The LLM can't see your staging API — it can't help generate or fix this

This is your team's test-data knowledge locked inside every spec file. A custom MCP turns it into one callable tool — the LLM uses it the same way it uses Playwright.

How It Works

What Happens When You Send a Prompt

Full flow — from your prompt to your test data
You type a promptin Copilot Agent Mode
→
LLM reads tool listfrom your MCP server
→
LLM decides:"I need seed_class"
→
VS Code sendsstructured tool call
The LLM constructs typed JSON arguments — your handler never receives free-form text
↕
LLM uses resultwrites it into the test
←
Your server returnsclassId: "42"
←
Handler runsauth → API → seed data
←
MCP serverreceives typed call

Tool list

When VS Code starts your server it calls tools/list. The LLM sees tool names, descriptions, and input schemas — that's how it knows seed_class exists and what arguments it accepts.

Typed call — not a prompt

Your handler receives structured JSON — { className: "Class A", studentCount: 5 } — never the user's raw sentence. Zod validates every argument at the boundary before your handler runs.

stdio transport

VS Code spawns your server as a local child process via node or npx. One entry in mcp.json. No port, no auth ceremony, no deploy step needed for local development.

2

Write the server — annotated line by line

import { McpServer }         from '@modelcontextprotocol/sdk/server/mcp.js';
import { StdioServerTransport } from '@modelcontextprotocol/sdk/server/stdio.js';
import { z }                 from 'zod';

// ① Container — name and version appear in tools/list
const server = new McpServer({
  name:    'test-data-factory',
  version: '1.0.0'
});

// ② Register a tool — 4 arguments
server.tool(

  'seed_class',                       // ② name — what the LLM calls

  'Seed a class with N test learners',  // ③ description — LLM reads this

  {                                     // ④ Zod schema — LLM must satisfy
    className:    z.string().describe('Tab label e.g. "Class A"'),
    studentCount: z.number().min(1).max(50)
  },

  async ({ className, studentCount }) => {  // ⑤ your handler
    const token    = await getToken();   // auth once — not in every spec
    const { classId } = await createClass(className, studentCount, token);
    return {
      content: [{ type: 'text', text: `classId=${classId}` }]
    };
  }
);

// ⑥ Connect — stdio pipe, VS Code manages the process
await server.connect(new StdioServerTransport());

2 Rules

Two Rules That Prevent Silent Failures

Rule 1 — Tool descriptions are LLM context. Keep them clean.

Wrong — secret in the description string

// description goes into EVERY prompt the LLM sees
server.tool(
  'seed_class',
  'Calls https://staging.signify/api
   with key sk-a8f7d2b1... for seeding',
  schema, handler
);
// ↑ Token + internal URL now live in LLM context

Right — env vars, checked at startup

// Description: only what the tool does
server.tool(
  'seed_class',
  'Seed a class with N test learners in staging',
  schema, handler
);

// Credentials: env vars, fail fast if missing
const API_KEY = process.env.TEST_DATA_API_KEY;
if (!API_KEY) throw new Error('TEST_DATA_API_KEY not set');
Rule 2 — Never accept a free-form string for a known set of values.

Wrong — free string for env name

// LLM sends "production" — URL breaks silently
{
  env: z.string()
  // "prod"? "production"? "PROD"? LLM guesses
}

// In the handler:
`https://${env}.signify/api/...`
// → https://production.signify/api — 404
// No error in chat. 30 minutes debugging.

Right — enum constrains LLM choices

// LLM sees the valid options — picks correctly
{
  env: z.enum(['staging', 'qa', 'uat'])
}

// In the handler — guaranteed to be one of three
`https://${env}.signify/api/...`
// → https://staging.signify/api — always correct

The other rules — read-only by default, no destructive ops without scoping, audit logs for writes — are real but come later. These two prevent the failures you'll hit on day one.
