Phase 2 — VS Code

Connecting MCPs in VS Code

How it works

  1. Add .vscode/mcp.json to your repo
  2. Reload VS Code: Ctrl+Shift+P → "Reload Window"
  3. Open Copilot Chat → switch to Agent mode
  4. Copilot auto-discovers available tools via tools/list
  5. Type a natural language prompt — Copilot picks the right tool

✅ Commit .vscode/mcp.json to Bitbucket — your whole team inherits the same MCP configuration automatically. No per-developer setup.

🔑 Use "${input:jira-token}" for secrets — VS Code prompts on first call and stores securely. Never hard-code credentials.

// .vscode/mcp.json — commit this to your repo
{
  "servers": {
    // Figma MCP (remote)
    "figma": {
      "type": "http",
      "url": "https://mcp.figma.com/mcp"
      // or desktop: "http://127.0.0.1:3845/mcp"
    },

    // Playwright MCP (local)
    "playwright": {
      "type": "stdio",
      "command": "npx",
      "args": ["@playwright/mcp@latest",
               "--allowed-origins=https://*.signify.com"]
    },

    // Atlassian MCP
    "atlassian": {
      "type": "http",
      "url": "https://mcp.atlassian.com/v1/mcp",
      "headers": {
        "Authorization": "Bearer ${input:atlassian-token}"
      }
    }
  }
}
Phase 2 — Configuration

Generating Tokens for MCP Authentication

🎨 Figma PAT

  1. Go to figma.com → Profile icon → Settings
  2. Scroll to Personal access tokens
  3. Click Generate new token
  4. Set scopes: File content: Read, Dev resources: Read
  5. Copy token — shown once only
  6. VS Code prompts on first MCP call → stored in OS keychain

🔗 Atlassian API Token

  1. Go to id.atlassian.com → Security → API tokens
  2. Click Create API token
  3. Label: signify-mcp-atlassian
  4. Copy token immediately — shown once
  5. Reference in mcp.json as ${input:atlassian-token}

One token covers Jira + Confluence + Bitbucket.

🎭 Playwright MCP No token — local process

Playwright MCP runs as a local stdio process — no API key needed. Just verify Node 18+ is installed:

npx @playwright/mcp@latest --version

If this prints a version number, you're ready — no auth steps required.

🔑 Never paste tokens directly into mcp.json. Use "${input:token-name}" — VS Code prompts on first call and stores the value in the OS credential store. The committed file contains no secrets.

Playwright MCP — How It Works

How Playwright MCP Sees Your App

❌ How most test recorders work

They read the DOM — implementation detail baked into the test.

// Breaks when ID or class changes
page.locator('#tab-class-a-btn')
page.locator('.LeaderboardTable_row__140Pj')
page.locator('xpath=//div[@data-v-12ab]')

Survey finding: "Every UI change breaks existing automation test suites due to changed HTML element IDs, locators, and selectors." — 180 Signify respondents

✅ How Playwright MCP works

It reads the accessibility tree — what a screen reader sees. Tied to user intent, not code structure.

// Survives class renames, ID changes,
// framework migrations
page.getByRole('tab', { name: 'Class A' })
page.getByLabel('Student name')
page.getByText('Show All Students')

Rename a CSS class, restructure a div, upgrade your component library — none of it breaks these selectors as long as the label stays the same.

📸 What the tool call looks like

Playwright MCP calls browser_snapshot — it gets back an accessibility tree, not HTML. The LLM writes tests from that tree.

🔁 The loop

LLM → browser_navigate → browser_snapshot → LLM sees tree → writes getByRole tests → browser_action runs them → result back to LLM.

🔑 The key insight

A screen reader can navigate your app without knowing HTML IDs. Your tests should too. That's Playwright MCP's default.

Playwright MCP — Prompting

Prompt Anatomy for Playwright MCP

The 4-part structure — every effective Playwright MCP prompt has these:
1

Trigger

Tell Copilot to use the browser. "Open a browser and navigate to…"

2

Context

Name the feature precisely. "…the leaderboard tab-switching feature…"

3

Framework

Pin the output format. "…using @playwright/test…"

4

Constraints

Set the selector rule. "…use only getByRole and getByText selectors."

✅ snap-code-project — ClassFilterTabs
// Good prompt → MCP invokes browser_navigate
"Open a browser at localhost:3000. Navigate to
the leaderboard section. The ClassFilterTabs
component has tabs for All, Class A, B, C.
Generate a @playwright/test for tab switching
— verify the leaderboard updates on each click.
Use only getByRole and getByText selectors."

Result: Copilot calls browser_navigate → browser_snapshot → writes tests with getByRole('tab', { name: 'Class A' }). No phantom selectors.

❌ What happens without a trigger
// No trigger → stays in chat mode
"Generate a Playwright test for the
leaderboard filter tabs."

// Copilot writes from memory — may invent
// selectors that don't exist in the real DOM:
page.locator('[data-testid="tab-all"]') // ← phantom
page.locator('#leaderboard-tab-1')      // ← phantom

Without "open a browser" or "navigate to", Playwright MCP tools are never called. You get plausible-looking tests that fail on first run.

snapshot vs screenshot: browser_snapshot returns the accessibility tree — use this for test generation. browser_screenshot returns a pixel image — use this for visual documentation or design comparison. They are not interchangeable.

Headed vs headless: MCP defaults to headed (visible browser window) — right for live demos and debugging. Set "headless": true in .vscode/mcp.json for CI runs where no display is available.

Playwright MCP — Selectors

Selector Hierarchy — Tests That Survive

Playwright MCP reads the accessibility tree first. Your prompt constraints determine how far down this hierarchy it goes. Keep it at the top.
1
getByRole('tab', { name: 'Class A' }) Most resilient

Tied to ARIA role + visible label. Breaks only if the feature semantics change — which is intentional.

2
getByLabel('Student name') Resilient

Tied to form label text. Survives HTML restructuring as long as the label copy stays.

3
getByText('Show All Students') Acceptable

Tied to visible copy. Add { exact: true } to prevent substring collisions.

4
getByTestId('leaderboard-row') Deliberate

Use when roles/labels aren't enough. Add data-testid intentionally — never let the AI invent a value that doesn't exist yet.

✕
#tab-class-a  .LeaderboardTable_row__xyz  xpath=//div[3] Never

Coupled to implementation. Every HTML refactor, CSS module rebuild, or React upgrade is a breaking change.

Encode this in your repo: add getByRole > getByLabel > getByText > getByTestId — never CSS IDs or XPath to your copilot-instructions.md. Playwright MCP will follow it automatically.

Playwright MCP — Anti-Patterns

Anti-Patterns & The Review Gate

5 things that burn teams
1

Committing tests you haven't read

Green ≠ correct. A test that passes while asserting the wrong thing is worse than no test — it gives false confidence.

2

Testing mock data only

Always run Playwright MCP against the actual rendered app at localhost:3000. Testing mockData.ts directly tells you nothing about the real UI.

3

Letting the AI invent data-testid values

If you ask for getByTestId without those attributes in the DOM, the AI invents names. Phantom selectors fail silently.

4

One prompt for the whole app

Context window discipline: one feature, one flow, one test file per prompt. Survey finding: "Chat session stops working when questions are big."

5

Skipping the selector review

Scan every generated selector. If you see a CSS ID, a class name with a hash, or XPath — rewrite it before committing.

6

Snapshotting before the page finishes loading

If content loads async (spinners, API calls), browser_snapshot may read a skeleton state. Instruct MCP to "wait until the leaderboard data is visible" before snapshotting — otherwise it generates tests against elements that don't exist in the loaded state.

The 3-question review gate

Before committing any AI-generated Playwright test, answer all three:

Q1

Does this test describe what I actually want to verify?

Read the assertion. Not the selector — the assertion. Does it match the user story?

Q2

Does it run against the real app?

Run it. Not just --dry-run. A real browser, real server, real data flow.

Q3

Would this test catch the bug if the feature broke?

Mentally break the feature. If the test would still pass — rewrite it. It's testing the wrong thing.

Shortcut: for ClassFilterTabs, manually comment out the onTabChange handler. The leaderboard test should fail. If it passes anyway, the test isn't verifying the filter.

Playwright MCP — Self-Healing

Self-Healing: Repairing Broken Tests

The survey pain: "Significant ongoing effort updating XPath and locator references rather than writing new tests." This is the repair workflow.
The 4-step repair loop
1

Test fails after UI change

CI goes red. A selector no longer matches the current DOM — class hash changed, ID removed, label reworded.

2

Paste the failing test + prompt Playwright MCP

Give it the broken test and ask it to navigate the live page and propose new selectors from the accessibility tree.

3

MCP reads the live accessibility tree

browser_navigate → browser_snapshot → proposes getByRole / getByText replacements that exist right now.

4

Review the repair — don't just accept

Did the selector change because the element moved, or because it was renamed? Verify the assertion still tests what you intended.

snap-code-project — LeaderboardTable

❌ Before — CSS Module class breaks on rebuild

// Generated by codegen — breaks on every
// CSS Modules rebuild or component rename
test('leaderboard shows correct student', async () => {
  await page.locator(
    '.LeaderboardTable_row__140Pj'  // ← hash changes
  ).first().click();
  await expect(page.locator(
    '#student-rank-1'               // ← ID removed
  )).toBeVisible();
});

✅ After — Playwright MCP proposes from live tree

// Prompt: "This test is failing after the last
// UI update. Navigate to localhost:3000 and
// suggest updated selectors using getByRole."
test('leaderboard shows correct student', async () => {
  await page
    .getByRole('row', { name: /Alice/ })  // ← stable
    .click();
  await expect(
    page.getByText('Rank 1', { exact: true })
  ).toBeVisible();                          // ← stable
});

Run the repair prompt once. Review the diff. Selectors tied to behavior, not HTML structure — won't break on the next CSS Modules rebuild.

The repair prompt pattern

"The test below is failing after a recent UI change.
Navigate to localhost:3000/[page], read the current
accessibility tree, and propose updated selectors
using getByRole or getByText. Do not change the
test logic or assertions — only fix the selectors.

[paste failing test here]"

⚠️ Review before you commit

  • Does the new selector target the same element?
  • Did the assertion intent change — or just the selector?
  • If the label changed in the UI, is the old test still valid?
  • Run the repaired test against a deliberate break to confirm it catches real failures.
Playwright MCP — Limits, Auth & CI

What You Still Need to Know

🚫 What Playwright MCP cannot do

  • Test mobile apps natively — use Appium for Android/iOS
  • Navigate pages behind login without auth setup (see centre column)
  • Interact with native OS dialogs (file upload pickers, alerts)
  • See inside cross-origin iframes
  • Test WebSocket real-time updates reliably
  • Replace visual regression tools — browser_screenshot is for documentation, not pixel diff

If your scenario hits any of these, say so in the prompt. MCP will tell you it can't proceed rather than generating something wrong.

🔐 Handling login / auth

Most Signify apps require authentication. storageState is the answer — do the login once, save the session, reuse it in every test.

// 1. One-time login script (run manually)
const browser = await chromium.launch();
const page = await browser.newPage();
await page.goto('https://app.signify.com/login');
// fill credentials, submit...
await page.context().storageState({
  path: 'auth.json'
});
// 2. playwright.config.ts — all tests reuse it
use: {
  storageState: 'auth.json'
}

Tell Playwright MCP: "The app requires login. Auth state is saved in auth.json — assume the session is already active."

⚙️ Running in CI (Jenkins / Azure DevOps)

The tests we generated run in any pipeline. One step is all it takes.

# Azure DevOps — azure-pipelines.yml
- task: NodeTool@0
  inputs:
    versionSpec: '20.x'
- script: |
    npm ci
    npx playwright install --with-deps chromium
    npm run test:e2e
  displayName: 'Run Playwright e2e tests'
  • Set "headless": true in MCP config for CI
  • Publish playwright-report/ as a pipeline artifact
  • Gate the PR merge on test pass

Jenkins: same script block inside a sh step. No Playwright-specific plugin needed.

The full picture: Playwright MCP generates tests from the live app → you review with the 3-question gate → tests commit to the repo → CI runs them headless on every PR → failures block the merge. That's the self-correcting automation loop.

Playwright MCP — Debugging

Debugging Failing Generated Tests

🎬 Step 1 — Run headed

Watch the browser execute the test in real time. Most failures become obvious immediately.

# Run one test in headed mode
npx playwright test \
  class-filter-tabs.spec.ts \
  --headed \
  --project=chromium

Add --slowmo 500 to slow each action by 500ms — easier to follow.

🔍 Step 2 — Open Trace Viewer

Full timeline: every action, the DOM snapshot before/after, network calls, console errors. Pinpoints exactly which line failed and what the page looked like.

# playwright.config.ts — enable on failure
use: {
  trace: 'on-first-retry',
  screenshot: 'only-on-failure'
}

# Open the trace after a failed run
npx playwright show-trace \
  test-results/*/trace.zip

🔬 Step 3 — Playwright Inspector

Interactive debugger — step through each action, inspect the accessibility tree live, pick selectors interactively.

# Run with inspector open
PWDEBUG=1 npx playwright test \
  class-filter-tabs.spec.ts

Also the fastest way to verify a selector before committing it to a test file.

Two most common failure patterns in MCP-generated tests

Selector not found — async content not loaded

MCP snapshotted the page before an API call completed. The element was in the loading skeleton, not the real content.

Fix: add to your prompt — "Wait until [specific content] is visible before snapshotting." Then regenerate with /repair-locators.

Assertion passes but tests the wrong thing

The element matched but the assertion doesn't verify the feature behaviour — it verifies that an element exists, not that it did the right thing.

Fix: apply the review gate Q3 — mentally break the feature and check if the test fails. If it doesn't, rewrite the assertion.

Playwright MCP — Flows & Isolation

Multi-Page Flows & Test Isolation

Multi-step flow prompt pattern

Describe the full user journey. MCP navigates step by step, snapshots at each stage, and generates a test that covers the whole flow.

Single-page (what we've shown so far)

"Navigate to localhost:3000 and test the leaderboard tab filter."
Works when everything is on one page.

Multi-page flow

"Navigate to localhost:3000/login. Log in as a coordinator. Navigate to the leaderboard. Click Class A. Verify the filtered results. Navigate back to the dashboard and verify the summary cards still show all classes."
MCP follows the full journey, snapshots at each step.

Rule: describe the journey the user takes, not the DOM you expect to find. MCP figures out the selectors from the accessibility tree at each step.

Test isolation — keeping tests independent

MCP-generated tests sometimes assume state from the snapshot they were written against. Isolate every test so it starts clean.

// ✅ Every test starts from a known URL
test.beforeEach(async ({ page }) => {
  await page.goto('/');
  // Wait for the page to be interactive
  await expect(
    page.getByRole('tablist')
  ).toBeVisible();
});
// ✅ Clear persisted state if your app uses it
test.beforeEach(async ({ page }) => {
  await page.goto('/');
  await page.evaluate(() => {
    sessionStorage.clear();
    localStorage.clear();
  });
});

Most common isolation bug

Test B depends on Test A having run first (e.g. Test A selects a tab, Test B assumes that tab is still active). MCP generates this because it snapshots in sequence. Fix: always navigate and set state explicitly inside each test — never rely on prior test state.

When MCP Isn't Available: Context Fallbacks

Not every server may be available when your team needs it. These fallbacks deliver most of the value without a live MCP connection — useful when a server isn't yet wired up.

🎨 No Figma MCP?

Export screens as a zip:

  • In Figma: select frames → Export as PNG + JSON spec → zip
  • Attach the zip to your Copilot agent chat
  • Prompt: "These are our design specs. Generate a React Native button matching screen-2.png"

⚠️ Best for small, scoped screens. Export one frame at a time — large files get noisy.

📋 No Atlassian MCP?

Export Jira story as HTML:

  • In Jira: open story → Print / Export as HTML
  • Save to specs/HUEAPP-1234.html in your repo
  • Prompt: "Read specs/HUEAPP-1234.html and generate test cases for each AC"

✓ Works today — open the file in VS Code or attach it to your Copilot agent chat.

🎭 No Playwright MCP?

Record tests offline with Playwright CLI:

  • Run npx playwright codegen [url] locally to record clicks into a test file — no MCP connection needed
  • Open browser DevTools → Elements → right-click element → Copy selector for manual locator hunting
  • Paste the generated test into Copilot chat: "Clean up these selectors to use getByRole instead of XPath"

✓ Works today — Playwright CLI is already available if Node.js is installed.

Phase 8 — Best Practices

7 Best Practices for Using MCPs at Signify

1. Vendor-official servers only

Only use servers from the Signify approved list or vendor-official servers pending review. No community servers without an internal security review.

2. Pin server versions

Use explicit versions in mcp.json (e.g. @playwright/mcp@1.50.0 not @latest). Review changelogs before upgrading.

3. Secrets via VS Code input vars

Use "${input:token-name}" for all API tokens. VS Code prompts once and stores in the OS keychain. Never commit credentials to Bitbucket.

4. Confirm before destructive actions

Enable tool-call confirmation in VS Code for any tool that writes, triggers builds, creates issues, or modifies files. Auto-approve only for read-only tools.

5. Scope your prompts

Ask for specific slices, not entire datasets. "Export only colour tokens" not "export all tokens". This prevents context bloat and faster responses.

6. Commit .vscode/mcp.json to Bitbucket

Share your MCP configuration with the team. Everyone gets the same setup. Include a comment in the file explaining each server and its status.

7. Task framing, not question framing

Prompts that describe a task invoke MCP tools. Prompts that ask a question get answered from training data. Use "get from Figma" not "what are the brand colours".
