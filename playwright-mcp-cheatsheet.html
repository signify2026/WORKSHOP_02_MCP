Core Concepts
How Playwright MCP Sees Your App
LLM prompt
→
MCP client
→
browser_navigate
→
browser_snapshot
→
Accessibility tree
→
Test code
Reads: accessibility tree — ARIA roles, labels, and states. Exactly what a screen reader sees.
Does NOT read: raw HTML, CSS class names, generated IDs. That's why tests survive refactors.
browser_snapshot → accessibility tree. Use for all test generation.
browser_screenshot → pixel image. Use only for visual docs — never for test generation.
Why accessibility tree selectors outlast everything:
CSS Module hash changes → test still passes
Component renamed → test still passes
UUI library upgrade → test still passes
HTML structure refactored → test still passes
Rename a CSS class, change an element ID, upgrade your component library — none of it breaks tests written from the accessibility tree.
Selector Hierarchy — Tests That Survive
1
getByRole('tab', { name: 'Class A' })
ARIA role + label → most resilient. First choice always.
2
getByLabel('Student name')
Form label association → survives HTML restructure.
3
getByText('Show All', { exact: true })
Visible text copy → always add exact:true.
4
getByPlaceholder('Search students...')
Input placeholder text → good for search inputs.
5
getByAltText('Student avatar')
Image alt text → use for <img> elements.
6
getByTitle('Sort ascending')
Title attribute → tooltip-driven UI elements.
7
getByTestId('leaderboard-row')
data-testid must exist in DOM — never invent.
✕
#id · .class__hash · xpath=//div[3]
Coupled to impl → breaks on rebuild.
Encode in copilot-instructions.md → Playwright MCP follows it on every tests/e2e/** file automatically.

Trigger required: without "open a browser", "navigate to", or "open localhost" in your prompt, Playwright MCP tools are never called — Copilot writes from memory and invents selectors.

Prompting, Assertions & Self-Healing
Prompt Patterns
/explore-app Opening beat
"Navigate to localhost:3000.
For each feature, describe:
- What a user can do
- What changes on interaction
- Accessible via: [role+label]
Do NOT write test code yet."
/explore-and-generate Generate
"Open localhost:3000.

/repair-locators Self-heal
"Test failing after UI change.
Navigate to [url], read the

[paste failing test here]"
/multi-page-flow Cross-page
"Navigate to /login.
Log in as [role].
Navigate to [page].

Assertions Quick Reference
Visibility & State
.toBeVisible()in DOM + visible
.toBeHidden()hidden or absent
.toBeEnabled()not disabled
.toBeDisabled()disabled attr set
.toBeChecked()checkbox/radio on
.toBeFocused()has focus
.toBeEditable()not readonly
.toBeEmpty()no text content
Page
.toHaveURL(/re/)URL pattern
.toHaveTitle('...')document title
Content & Attributes
.toHaveText('...')exact text match
.toContainText('x')substring match
.toHaveValue('x')input value
.toHaveAttribute()HTML attribute
.toHaveClass('x')CSS class present
.toHaveCount(n)exactly n matches
.toHaveValues([])multi-select opts
Soft Assertions
// don't stop on fail
await expect.soft(el)
  .toBeVisible();
expect(test.info()
  .errors).toHaveLength(0);
Prefer semantic assertions — always test what the user would notice:
expect(count).toBeTruthy() — tells you nothing meaningful
expect(page.getByRole('row')).toHaveCount(25) — tells you filtering worked
Self-Healing Workflow
1
Test fails after UI change
CSS hash changed, ID removed, label reworded. CI goes red.
2
Run /repair-locators
Paste the failing test. MCP navigates the live page, reads the current accessibility tree.
3
MCP returns updated selectors
Proposes getByRole / getByText replacements grounded in what actually exists now. Never touches assertions.
4
Review repair — don't just accept
Did the selector change because the element moved, or because the feature changed? Verify the assertion still tests the right thing.
3 review gate questions before committing
Q1Does this test describe what I want to verify?
Q2Does it run against the real app, not mocks?
Q3Would it catch the bug if the feature broke?

Flakiness Prevention
Never use page.waitForTimeout(ms) — hardcoded sleep = flaky test
Use expect(locator).toBeVisible() — Playwright retries with timeout
Use browser_wait_for in prompt before snapshotting async content
Set retries: 2 in CI — catches one-off race conditions
Detect flaky: npx playwright test --repeat-each 5
Isolate state — beforeEach goto + clear storage
MCP: snapshot before async API resolves → tests target loading skeleton. Tell it: "Wait until [content] is visible before snapshotting."
Test Isolation
Each test must start from a known clean state — MCP tests assume the state at snapshot time.
// ✅ Navigate + clear storage before every test
test.beforeEach(async ({ page }) => {
  await page.goto('/');
  await page.evaluate(() => {
    sessionStorage.clear(); localStorage.clear();
  });
  await expect(page.getByRole('tablist')).toBeVisible();
});
// ✅ One feature per describe block
test.describe('ClassFilterTabs', () => { /* group by behaviour */ });
Never let Test B depend on Test A having run first
Set explicit state in each test — never rely on prior side effects
fullyParallel: true enforces isolation — if tests share state, parallel runs expose it immediately.
Auth, Network & Accessibility
Auth / storageState
Log in once in globalSetup, save the browser session, reuse across all tests.
// setup.ts — runs once before all tests
import { chromium } from '@playwright/test';
export default async function globalSetup() {
  const browser = await chromium.launch();
  const page = await browser.newPage();
  await page.goto('https://app/login');
  await page.getByLabel('Email').fill('user@company.com');
  await page.getByLabel('Password').fill(process.env.TEST_PASS!);
  await page.getByRole('button', { name: 'Sign in' }).click();
  await page.waitForURL('**/dashboard');
  await page.context().storageState({ path: 'auth.json' });
  await browser.close();
}
// playwright.config.ts
export default defineConfig({
  globalSetup: './setup.ts',
  use: { storageState: 'auth.json' }
});
Never commit auth.json — add to .gitignore
Tell MCP: "Auth state is saved in auth.json — session is already active."
Network & API Mocking
Intercept requests to isolate front-end behavior, test error states, prevent external calls in CI.
// Mock API response
await page.route('**/api/students', route =>
  route.fulfill({ json: mockStudents, status: 200 })
);

// Assert real API was called
const [res] = await Promise.all([
  page.waitForResponse('**/api/students'),
  page.getByRole('button', { name: 'Load' }).click()
]);
expect(res.status()).toBe(200);
// Test error state
await page.route('**/api/students', route =>
  route.fulfill({ status: 500, body: 'Server Error' })
);
await expect(page.getByRole('alert')).toContainText('Failed to load');

// Block 3rd-party trackers in CI
await page.route('**/{analytics,tracking,ads}**', r => r.abort());
Use browser_network_requests MCP tool to inspect API calls after a user action — no code needed.
Accessibility Testing
Playwright MCP already reads the accessibility tree. Add axe-core to run WCAG audits as part of your suite.
// Install: npm install --save-dev @axe-core/playwright
import AxeBuilder from '@axe-core/playwright';

test('has no WCAG violations', async ({ page }) => {
  await page.goto('/dashboard');
  const results = await new AxeBuilder({ page })
    .withTags(['wcag2a', 'wcag2aa']).analyze();
  expect(results.violations).toHaveLength(0);
});

// Scope to a component
const results = await new AxeBuilder({ page })
  .include('#leaderboard-table').withTags(['wcag2aa']).analyze();
MCP's accessibility-tree selectors are inherently a11y-aware — using getByRole proves ARIA is correct
Run axe audit on every page as a separate test file — keep it isolated from interaction tests
browser_snapshot + browser_console_messages MCP tools can reveal missing labels and ARIA errors during exploration
axe-core scoping methods
.include('#component-id') — scope audit to one region
.exclude('#cookie-banner') — skip known 3rd-party widget
.withTags(['wcag2a','wcag2aa']) — target conformance level
.disableRules(['color-contrast']) — suppress known issues temporarily
CI / CD
CI / CD Pipeline Reference Azure DevOps & Jenkins — both use the official Playwright Docker image in CI
Azure DevOps — azure-pipelines.yml
# azure-pipelines.yml
trigger:
  branches:
    include: [ main, 'feature/*' ]

pool:
  vmImage: ubuntu-latest

steps:
  - task: NodeTool@0
    inputs:
      versionSpec: '20.x'
    displayName: 'Install Node 20'

  - script: npm ci
    displayName: 'Install dependencies'

  - script: npx playwright install \
      --with-deps chromium
    displayName: 'Install Playwright'

  - script: npm run test:e2e
    displayName: 'Run E2E tests'
    env:
      TEST_PASS: $(TEST_PASS)  # secret var
      CI: 'true'

  - task: PublishTestResults@2
    condition: always()
    inputs:
      testResultsFiles: >
        playwright-report/results.xml
      testRunTitle: 'Playwright E2E'

  - task: PublishBuildArtifacts@1
    condition: always()
    inputs:
      pathToPublish: playwright-report
      artifactName: playwright-report
Store TEST_PASS as a secret variable, not in YAML. Add condition: always() to publish steps so artifacts save even on failure.
Jenkins — Declarative Pipeline (Jenkinsfile)
// Jenkinsfile
pipeline {
  agent {
    docker {
      // Official image — browsers pre-installed
      image 'mcr.microsoft.com/playwright:v1.49.0-jammy'
      args  '-u root'
    }
  }

  environment {
    TEST_PASS = credentials('app-test-password')
    CI        = 'true'
  }

  stages {
    stage('Install') {
      steps { sh 'npm ci' }
    }

    stage('E2E Tests') {
      steps {
        sh 'npm run test:e2e'
      }
      post {
        always {
          publishHTML([
            reportDir:   'playwright-report',
            reportFiles: 'index.html',
            reportName:  'Playwright Report'
          ])
          junit 'playwright-report/results.xml'
        }
      }
    }
  }

  post {
    failure {
      archiveArtifacts 'test-results/**'
    }
  }
}
Use mcr.microsoft.com/playwright official Docker image — browsers are pre-installed, no separate install step needed.
Limits & Anti-Patterns
What Playwright MCP Cannot Do
Mobile native apps — use Appium for Android/iOS. Playwright is web-browsers only.
Cross-origin iframes — accessibility tree stops at the iframe boundary.
Native OS file dialogs — file picker is outside browser sandbox. Use browser_upload_file to set the path directly.
WebSocket live updates — accessibility tree is point-in-time, not a live stream.
Canvas / WebGL rendering — visual content has no accessibility tree nodes.
Pages behind SSO/login — without storageState (see Auth card).
Visual pixel regression — use Percy / Chromatic. browser_screenshot captures images but cannot diff them.
Performance load testing — Playwright MCP is functional. Use k6 / Lighthouse for perf.
CAPTCHA challenges — deliberately resist automation.
Email / SMS verification — outside browser context. Use Mailosaur or similar.
If your scenario hits any of these limits, state it in the prompt. MCP will flag it rather than silently generating broken tests.
Anti-Patterns — The 8 Things That Burn Teams
Committing tests you haven't read. Green ≠ correct. Read the assertion — not just the selector.
Using waitForTimeout. Replace every sleep with expect(locator).toBeVisible().
No browser trigger in the prompt. Without "open browser" / "navigate to", MCP writes from memory → phantom selectors.
One prompt for the entire app. Context overload. One feature → one prompt → one test file.
Inventing data-testid values. If the attribute doesn't exist in the DOM, the test silently fails.
Testing mock data only. Run against localhost:3000 — real render, real data flow.
Snapshotting before page loads. Always add a wait instruction before browser_snapshot for async content.
Test order dependencies. Test B assumes Test A ran first. Set explicit state in every beforeEach.

// suite-level serial (avoid)
test.describe.configure({
  mode: 'serial'
});

// suite-level parallel (default)
test.describe.configure({
  mode: 'parallel'
});
fullyParallel: true — each test gets own browser context
Set workers: 1 for debugging — easier trace following
Each worker gets own storageState copy — auth works in parallel
Never write to shared DB state in parallel tests without seeding isolation
CI: workers: 2 conservative; local: undefined = auto (cores ÷ 2)
